# 接続元IPによる追加制限の準備

2026-10-16。開発ブランチだけの準備。APIへ未接続、本番・検証へ未配備。許可IP、信頼する取得方法、保存期間、回数上限は未設定。一般受付OFF・メール停止を変更しない。

## 現状と今回の実装

現行の顧客APIはCAPTCHA、連絡先別の送信回数制限、顧客メール全体枠、本人確認、管理者認証を持つ。接続元IPの信頼確認とIP別制限はまだない。これらを重複実装しない。

`integrations/cargo-safety-preparation/operator-ip-policy.ts` は管理者・本人限定試験に追加する許可リストの**照合部品だけ**。API、固定配備候補、画面、環境設定から呼ばない。

- 初期値は無効・空リスト。未設定・無効・不正な設定では一致を返さない。
- 最大64件の単一IPとの完全一致だけを扱う。IPv4/IPv6の同値表記とIPv4-mapped IPv6を統一する。CIDR、ワイルドカード、ホスト名、ポート、IPの列、前後の空白、省略IPv4等は拒否する。
- 不正・重複した許可項目が1つでもあれば設定全体を無効として扱う。誤った項目を読み飛ばして部分的に有効化しない。
- 結果は一致の有無と固定コードのみ。IPを返さず、通信・ヘッダー読取・秘密値読取・保存・記録を行わない。試験のIPは文書用の予約範囲だけ。
- 一致しても `source_verified=false`、`enforcement_ready=false` を返す。**取得元の信頼確認や本人認証の代わりにはならず、アクセス許可を意味しない。**

64件は部品の入力上限で、運用上の許可件数の決定ではない。無効状態の部品を導入したことをIP制限の完成と扱わない。

## 接続前に技術的に確認すること

1. 現行の受付・管理者画面はSupabaseへ直接 `functions.invoke` し、回答画面もSupabaseの関数URLへ直接通信する。`app.rainbow-driver.com` のOriginや静的画面がCloudflare経由で配信されたことは、APIの接続元の証明にならない。公開画面から関数までの実経路と、関数URLへの直接アクセス経路を確認する。
2. 基盤がどの接続元情報を上書き・検証するか、その保証を公式資料と限定的な検査で確認する。`X-Forwarded-For` の先頭/末尾、`Forwarded`、`X-Real-IP`、`CF-Connecting-IP` 等を推測で採用しない。ソケットの相手が中継サーバーの場合も、利用者のIPとして扱わない。
3. 中継経路・信頼する取得箇所を固定した専用処理を追加する。その前段を迂回できる経路を閉じられないなら、その方法を採用しない。欠落・重複・矛盾・不正な値・取得失敗時に拒否できることを、直接通信も含めて検査する。
4. その処理から得た単一IPだけを照合部品へ渡す。JWTの検証、管理者所属、本人限定の対象/期限/一回性、停止スイッチ等の既存保護を必須のまま併用する。接続元IPが一致してもそれだけで本人と判断しない。

ここまでは運営者の許可IP選定を待たず調査・設計できる。今回、基盤の取得保証は未確認であり、実通信によるIP取得試験は行っていない。Supabase Authの匿名ログイン向けIP制限や関数間通信の制限は、この顧客用Edge APIの接続元情報が上書き・検証される保証の代わりにはしない。

## 一般のお客様向けの回数制限は別に設計する

管理者・本人試験の許可リストを一般受付の顧客へ適用すると、対象外の顧客をすべて拒否する。一般受付の不正利用対策は、信頼できる接続元の取得後、IP別の試行回数を制御する仕組みとして分ける。

- 受付開始・コード照合・回答等のどの操作を数えるか、時間枠・回数・保管期間を決める。共有回線や携帯回線、IPv6でIPが変わる場合の誤拒否と回避の可能性も考慮する。値は未設定のまま。
- 複数の関数インスタンスで同時に処理しても上限を守る、期限と件数が制限されたDB側の処理が必要。関数内メモリーだけのカウンターを実用の制限として採用しない。成功前に枠を確保し、通信結果不明時の自動返還・再送を行わない。
- 生IPをアプリDB・ログ・画面へ残さない。必要なら用途を分けた秘密鍵によるHMAC等の識別子を検討する。単なるハッシュでは全IPv4を推測できる。HMACでも匿名情報とは断定せず、鍵管理・更新・保存期間・削除を設計する。本番と検証の鍵を共有しない。
- 接続元の取得失敗・DB失敗・上限超過時の応答は固定コードだけとし、IP・認証情報・本文を出さない。一般受付OFFの確認を優先し、停止中に新しいカウンターや記録を増やさない。

既存のメール別制限と全体枠は維持する。IP制限を追加しても、配信サービスの契約上限、DDoS防御、全経路の不正利用防止を満たしたとは扱わない。

## 残る判断と検査

- 運営者判断：追加制限の対象、許可する接続元（固定IPが使えるか等）、一般受付の制限値と記録の保管方針。実値はGitやチャットへ記載せず、安全な設定経路を使う。
- 技術調査：基盤の信頼できるIP取得保証、直接アクセスによる迂回の可否、確実に拒否できる接続方法。保証が確定するまで未接続・無効を維持する。
- 実装後の検査：許可/不許可/欠落/偽装ヘッダー/表記違い、停止、同時実行、設定欠落、DB障害、期限削除。今回の単体試験は照合部品だけを対象とし、実経路の制限を確認した扱いにしない。
