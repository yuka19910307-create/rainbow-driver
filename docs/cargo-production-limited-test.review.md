## 本番限定試験の実行案（制限完成・具体的承認後のみ）

目的は本番固有の設定・配信・保存・照合・終了を最小の一巡で確認すること。検証済みの全機能を最初から繰り返す試験ではない。

| 項目 | 限定範囲 |
| --- | --- |
| 接続先 | 本番プロジェクトと本番サイトのみ。実行前に実接続先を確認 |
| 操作者・宛先 | 本番の確認済み運営者認証アカウント本人1人、そのアカウントに紐づく本人メール1先 |
| 案件 | サーバー固定の架空案件1件。実在の依頼人・詳細住所・電話番号を使わない |
| 入力例 | 集荷「テスト集荷地・伊奈町」、配送先「テスト配送先・さいたま市」、荷物「本番接続確認用の架空の箱」、氏名「テスト担当者」。試験用である旨を備考と見積条件へ記載 |
| 金額・条件 | 試験前に運営者が指定した架空金額・架空条件だけ。未入力なら開始不可。正式料金表・最低料金・税・追加料金の決定へ転用しない |
| 操作時間 | 開始から最大30分。途中のやり直し・延長なし |
| 送信 | 認証コード1通＋見積もり1通、送信試行最大2回。再送なし |
| 回答 | 正規メールから閲覧し「利用希望」1回を記録。契約・配車・配送・決済を作らない |
| 公開状態 | 一般受付OFFを維持。一般利用者の入力受付を開始しない |

1. **送信前の読取**：接続先、配備版、一般受付OFF、保護設定、試験未開始、顧客件数と送信試行数の基準値を確認する。送信設定の存在・形式だけでなく、配信事業者の送信元認証・本番利用条件・利用上限・残量・他経路の利用を権限のある画面で確認する。秘密値そのものは記録しない。設定や残量が未確認なら開始しない。
2. **本人が一度だけ開始**：制限済みの本番試験画面で本人がログインし、固定の架空入力・宛先の本人一致・架空見積内容・期限・上限を確認する。試験開始は送信と分け、開始しただけでメールを送らない。
3. **OTPを一度だけ送信・確認**：本人がCAPTCHAを通し、認証メールを1回送信する。本人が受信箱で到着を確認し、10分以内にコードを画面へ入力する。コードをチャットへ送らない。依頼1件の作成と管理者側の復号表示を確認する。
4. **見積もりを一度だけ送信・確認**：同じ架空案件だけを審査し、事前確認済みの架空見積を保存する。保存した金額・条件・期限を照合し、残り時間が不足しなければ本人が1回送信する。配信事業者の受付と本人の受信箱への到着を別々に記録する。
5. **リンクと一度だけの回答**：本人がメール内リンクから本番の回答画面を開き、金額・条件・期限と非契約の案内を確認して利用希望を1回記録する。管理者側で同じ案件の回答状態を確認する。回答リンクを転送・貼付・スクリーンショット化しない。再回答や別メールの追加送信で一回性を試さない。
6. **終了・停止・保管**：次項に従い直ちに試験を閉じる。期限の自動停止を待つために送信可能状態を残さない。

必要な本人操作はこの一巡にまとめる。途中失敗を理由に別枠を作る・検証枠へ戻る・メールを再送する依頼は行わない。実行時に取得する証拠は時刻、接続先、版、制御フラグ、件数、試行数、秘匿化した結果分類に限る。

## 停止条件と終了処理

次のいずれかで直ちに試験を停止する：接続先や版の不一致、一般受付ON、本人・宛先・案件の不一致、保護設定不備、未承認の架空見積内容、試行上限超過または計数不明、重複案件、復号不良、権限逸脱、期限不足、タイムアウト、送信結果不明、受信未確認、回答保存の不一致、停止・監視の異常。期待した到着が確認できなければ、残時間内に受信箱を確認するだけとし、試験期限で未完了終了する。

1. 本人限定試験を無効化し、追加送信権を停止する。一般受付OFF・試験用送信停止・顧客メール全体枠 `enabled=false` を読取確認する。全体枠を試験のために変更する設計を採用した場合も、終了時に必ず無効へ戻す。
2. 試験の終了時刻・失効状態、OTPと見積もりの試行回数がそれぞれ1以下、合計2以下、対象外案件の増加がないことを確認する。上限の使用記録・一回性の記録は戻さず、認証・送信・回答の再開始を拒否する。
3. 送信中・結果不明の場合は、配信事業者と保存状態を権限のある画面で照合する。自動再送、`ready_to_send` への書戻し、送信数の減算、保留中の証跡削除を行わない。結果不明のまま成功・削除完了と報告しない。
4. 正常終了の架空案件は、契約・配送・決済がないことを確認して既存の `close_no_order` 操作で閉じ、終了から30日後の削除対象とする。フォロー記録を作っていない一巡を基本とし、フォローがある場合の終了操作が一般受付ONを要求する現行制約は、試験制限実装時の課題として解消する。OFFを解除して閉じない。
5. 下書き・案件の期限を過去へ書き換えず、即時DELETEや初回導入SQLの再実行を行わない。送信結果不明や保管の必要がある案件は保留を維持する。削除関数が存在することと定期削除が稼働することを区別し、削除期限、実行担当、実行/定期処理の導入状況、後日の削除確認日を記録する。定期処理がなければ自動削除済みと扱わない。
6. 成功した工程と失敗・未確認の工程を分けて報告する。受信箱の到着、管理者保存状態、停止状態の実確認がそろった工程だけを完了にする。一般受付開始の可否は別の判断として残す。
