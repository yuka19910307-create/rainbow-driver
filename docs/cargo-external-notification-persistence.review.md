# 外部異常通知のローカル状態保存と排他制御

2026-10-16 UTC。PR #5までの通知候補作成を土台に、`scripts/cargo-monitor-notification-store.cjs` を追加した。既存の監視分類・通知状態の純粋関数は変更していない。今回動かしたのは隔離した架空データのファイル保存だけであり、外部通知、実行元の導入、DB接続、本番設定変更は行っていない。`enabled=false`、`destination=null`、`automatic_retry=false`、`dispatches=0` を既存の固定設定から維持する。送信処理・ネットワークライブラリ・通知先の設定口は追加していない。

## 実装した範囲

Nodeの標準機能だけを使う、プログラムから呼び出すローカル保存部品。既存の `prepare` / `claimAttempt` / `settleAttempt` を再利用し、固定コード・時刻・イベント番号・送達状態だけからなる通知準備状態を保存する。入力の読取結果そのもの、顧客情報、任意のエラー本文、アドレス、秘密値は保存・ログ出力しない。エラー出力も固定コードに限定し、保存場所や生のOSエラーを転記しない。

| 操作 | 動作 |
| --- | --- |
| `initializeStore(absoluteDirectory)` | 新規のディレクトリだけを明示的に作り、revision 0を保存。既存ディレクトリは空でも拒否 |
| `readStore(absoluteDirectory)` | 保存済みの状態とrevisionを排他的に読む。欠落・破損を初期状態に戻さない |
| `observeStore(directory, {expected_revision, snapshot, read_succeeded, now})` | 既存分類器で観測を処理し、期待revisionが一致した場合だけ保存。snapshot / read_succeeded / nowは必要に応じて省略可 |
| `claimStore(directory, {expected_revision, event_id})` | 最新の未着手イベントだけを`attempt_started`へ保存。これは架空の送達帳簿処理であり、通知を実行する許可や送信処理ではない |
| `settleStore(directory, {expected_revision, event_id, outcome})` | 同じイベントの`attempt_started`だけを`confirmed` / `failed` / `unknown`へ保存。任意本文やエラーを受け取らない |

`revision`はイベント番号とは別に各保存で増加する。同じ状態を別プロセスが先に保存した場合、古いrevisionからの更新は拒否する。過去のイベントへの遅い結果も新イベントへ適用しない。保存値はJSONとして65,536バイト以内、履歴は既存設計どおり現在の通知状態1件だけとし、無制限の履歴・送信待ち行列・保存期間・自動削除は追加しない。

既存モジュールは内部の厳密な状態検証をexportしていない。そのコードとCI対象を変更せず重複検証も作らないため、保存時には `prepare({state, read_succeeded:false, now:前回確認時刻または0})` を検証用に呼ぶ。返された仮の観測・イベントはすべて破棄し、入力状態は変更しない。この結合を専用試験で確認している。検証用の呼出しがイベント番号の安全な整数上限などで拒否される場合は、状態を初期化せず処理停止とする。revision上限でも同様に停止する。

## 保存と並行実行

1. 保存先は実行ユーザー所有の非公開ディレクトリ（0700）、状態ファイルは0600。祖先のシンボリックリンク、rootまたは実行ユーザー以外の所有、group/other書込可能な祖先を拒否する。root所有のstickyな一時ディレクトリだけは祖先として許容する。
2. 読取・更新とも `.lock` ディレクトリの排他的な作成で占有し、その作成を親ディレクトリのfsyncで確定する。他プロセスは待機や上書きをせず拒否される。古いロックも経過時間で奪取しない。
3. 保存先の通常ファイル・所有者・非公開権限・単一リンクを確認し、`O_NOFOLLOW`で開く。シンボリックリンク、ハードリンク、不明な追加ファイル、残った `state.next` は拒否する。
4. 期待revisionを確認した後、新しい状態を `state.next` へ `O_EXCL`で新規作成し、ファイルfsync → rename → 保存ディレクトリfsyncの順で確定する。ロックのinodeは保存直前・rename直前・保存確定後にも確認する。
5. ロック解除とそのディレクトリfsyncまで成功した場合だけ、claimの成功を返す。保存途中や保存確定が不明な場合は成功を返さず、ロックや一時ファイルの証拠を保持する。

プロセスが保存途中で終了したとき、次の起動が欠落・ロック・一時ファイルを検出したとき、ファイルが破損したときに、自動修復・再初期化・自動再試行・ロックの自動解除はしない。確認者はまず実行元を停止し、保存済み状態と証拠を保全して確認する必要がある。ロックを消すことや新しい保存先を作ることで同じイベントを再送可能にする復旧手順は未実装。保持期限やロック失効時間は推測で設定していない。

## 送達不明と復旧

`attempt_started` / `unknown` / `failed` の状態では、同じイベントの再claimも、新しい観測によるイベント置換も拒否する。監視上は復旧した場合でも、未解決の送達証拠を失って新しい通知へ進むことはない。確認待ちの間に次の候補を蓄積する仕組みや、未解決状態を解除する運営手順は今回追加していない。

送達確認済みの状態では、より新しい異常・復旧を既存の分類規則で扱う。未送信の`prepared`同士は既存設計どおり最新の候補へ置き換えられ、過去候補の送達が確認されていないことをフラグで保持する。全イベントの履歴保存ではない。実際の通知先側の照合・到達確認・安全な再通知には、別途の設計と承認が必要。

## 保証の前提と未実装

今回の排他・永続性は、同じ保存先を使う単一ホストの協調プロセスと、rename・排他的な作成・fsyncを正しく実装する耐久性のあるローカルファイルシステムが前提。複数ホスト、NFS/分散ファイルシステム、ホストをまたぐコンテナ、保存先の巻き戻しや全損、悪意ある同一ユーザー/管理者、実機の電源断耐久性は検証していない。複数の独立した保存先を使った重複通知は防げない。採用する実行元・永続ディスク・保存先の固定化は未決定で、本番運用可能な外部通知として扱わない。

未実装は、外部の定期実行元、実行元停止の検知、通知先との接続、実通知、到達確認、送達不明の手動照合/解除手順、履歴の保存方針。公開メールアドレスやLINEを通知先へ流用していない。今回の部品に一般受付・顧客メール・契約・配車・決済へ接続する経路はない。
