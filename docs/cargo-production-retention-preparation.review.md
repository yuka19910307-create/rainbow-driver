# 本番の定期削除を登録する前の準備

2026-10-16 UTC。以下は開発コードであり、本番/検証の登録・削除・設定変更はしていない。

既存の下書き削除 `cargo_customer_intake_cleanup(100)` と終了案件削除 `cargo_customer_closed_cleanup(100)` を使う。新しい削除関数やスケジュール登録スクリプトは追加しない。既に導入した初回SQLも再実行しない。

## 追加した読取と判定

`integrations/cargo-production-maintenance/retention-preview.readonly.sql` はSELECTだけで、次を集計する。削除関数を呼び出さず、行をロックせず、顧客ID・本文・暗号化値・連絡先・ジョブコマンド・失敗本文を出さない。

- 下書き削除の対象総数と最大100件の予定数。認証済み下書きも既存関数と同じ条件で数える。
- 30日経過・明示終了・保存保留なし・継続フォローなし・送信中/結果不明なしという、既存関数と同じ条件による終了案件の対象総数。先頭100件に紐づく見積もり、フォロー、イベント、消去可能な認証済み下書きの予定数。
- 保存保留、継続フォロー、送信未解決の保護対象の件数。分類は重複するため合計しない。
- 同名ジョブ、別名で既存削除関数を含むジョブ、稼働中/別DBの件数。停止中も数え、同名上書きや二重登録を避ける。コマンドの文字列照合であり、ラッパー関数等を含むすべての経路を見つける検査ではない。
- アプリの削除実行履歴と、上記関連ジョブのCron履歴件数。他業務のCron履歴本文は取得しない。削除済みジョブの孤立履歴はこの集計に入らないため、別途対象の特定が必要。

接続先プロジェクトを権限のある画面で別途確認したうえで使う。`scope`は形式ラベルであり本番接続の証明ではない。SQLが失敗した場合は未確認とし、権限を一般利用者へ開けて解消しない。

JSONオブジェクトだけを `node scripts/check-cargo-retention-preview.cjs < preview.json` へ渡すと、5分超の古さ、不正な件数、100件上限との不整合、既存ジョブの衝突を固定コードで検出する。入力上限を設け、生の入力を出力しない。通信・接続・登録・実行・削除・送信の機能はない。正常でも `review_only=true`、`execution_enabled=false` を返し、実行承認とは扱わない。

`ok=true`は集計の形式・件数関係と既存ジョブの不存在を確認した意味だけで、受付停止・メール停止・権限保護を確認した意味ではない。これらは既存の `production-monitor.readonly.sql` と `check-cargo-production-monitor.cjs` を併用して別途確認する。

下書きと終了案件の2種類の予定数は独立した見積もり。同じ下書きが両方の対象となり得るため合計しない。読取中はロックを取らず、既存関数は実行時点とロック状況で対象を取り直す。したがって、予定件数は削除件数の確約や削除許可リストではない。

## 未設定のまま保留するもの

| 項目 | 今の扱い |
| --- | --- |
| 終了後の保存期間 | 採用済みの30日を維持。継続案件や保存保留を自動解除しない |
| 本番ジョブの登録/有効化 | 未実施。今回の実装から登録も起動もできない |
| 実行間隔 | 下書き5分/終了案件毎時17分は既存監視の候補。運営者が承認済みの値と推測して登録しない |
| 削除履歴/Cron履歴の保存期間・消去上限 | 未設定。推測した日数で履歴削除を実装しない |
| 本番の削除実行条件と担当 | 承認待ち。データ0件でも接続試験としてcleanupを呼ばない |

将来登録する前には、新しい本番監視結果で受付OFF・メール停止・権限保護を確認し、このプレビューと既存ジョブを照合する。ジョブがある場合は同名でも別名でも登録を止めて確認する。間隔・履歴方針・担当・実行範囲の承認後、登録と初回実行を別の変更としてレビューする。今回の本番配備禁止と顧客削除禁止は継続する。

## 変更に対する検証

ローカル分類試験は有効な匿名集計、古い/未来時刻、不正件数、既存ジョブ、入力上限、秘密本文を出さない動作を検査する。新規の隔離PostgreSQL試験は読み取り専用トランザクションでの実行、13種類の架空データでのプレビューと既存2削除関数の件数一致、ジョブ衝突検出の計15検査を行う。保留・継続・送信中・結果不明の除外と100件上限を含む。101件の境界前後で関連レコードの分布を変え、終了時刻・IDの順序も確認する。専用DB内の変更だけをロールバックし、実サービス・終了済み本人試験とは切り離す。

参照：[Supabase Cron Quickstart](https://supabase.com/docs/guides/cron/quickstart)（2026-10-16に公式ドキュメント検索で確認）。同名scheduleの上書き、Cron履歴の非自動削除、ジョブ削除後の履歴残存を前提にする。
