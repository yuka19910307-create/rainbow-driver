# 通知状態の安全診断

2026-10-16 UTC。PR #6までの保存部品を変更せず、`scripts/check-cargo-notification-state.cjs` を追加した。既存の `readStore` 等が返した値を解釈する、オフラインの純粋関数とstdin CLIである。ファイル読取、ロック操作、DB接続、実行元起動、通知送信、保存状態の修復は行わない。通知先はnull、送信無効、dispatchesは0を維持する。

## 入出力と意味

`assess(storeResult)` は、既存storeの戻り値の6項目（configuration、dispatches、status、issues、revision、state）を受ける。状態の形式検証には既存通知kernelの `prepare` を検証用に再利用し、仮の読取失敗結果を破棄する。既存kernel/storeの変更や、状態検証規則の複製はしていない。

| 保存記録・結果 | 診断 |
| --- | --- |
| 初期状態 | `NOT_OBSERVED`。監視の基準を取得した証拠はない |
| 正常・異常・復旧・監視読取失敗・読取復旧 | `RECORD_ONLY`。観測とイベントを別の固定コードで表す |
| `attempt_started` / `unknown` / `failed` | `DELIVERY_REVIEW_REQUIRED`。実行元停止・証拠保全・人による送達照合待ち |
| `STORE_LOCKED`、保存欠落/破損、更新競合など既知の停止コード | `STORE_REVIEW_REQUIRED`。原本を保全し、保存状態の確認待ち |
| 項目欠落、未知のschema/状態/停止コード、余分な項目、有効化設定、矛盾する操作名・revision | `INVALID_INPUT`。正常に置き換えず停止 |

出力は固定コードと固定設定だけ。入力の時刻、イベント番号、revision、異常の本文、パス、通知先、秘密値、元のstateは出力しない。`diagnostic_valid=true` は既知の戻り値形式として解釈できたという意味だけで、取得元の真正性、現在の正常性、実際の通知到着を証明しない。過去の正常/確認済み記録にも `CURRENT_RUNTIME_UNVERIFIED` と `NO_DELIVERY_PERMISSION` を必ず付ける。

`dispatch_allowed`、`retry_allowed`、`reset_allowed`、`unlock_allowed`、`resume_allowed` はどの入力でもfalse。残留ロックを消す操作、別の保存先で初期化する操作、再claim、再送、保留解除を指示する経路はない。既知の停止コードだけを許可リストで扱い、未知のエラー本文は転記しない。

CLIは引数を受けず、stdinのJSONだけを最大65,536バイトまで読む。不正UTF-8/JSON・超過・読取エラーは固定コードで終了する。解釈できる記録も終了コードは1、不正入力は2で、0を実行許可と誤認する経路を作らない。ローカル保存先を渡しても読まず、引数自体を拒否する。

## 未解決状態を見つけたとき

自動処理を再開せず、原本の状態と中断時の証拠を保持する。ロックの存在だけで、稼働中か中断後かは判定しない。送達開始・不明・失敗の記録も、「届いていないから再送してよい」と解釈しない。

実行元の確実な停止、原本の安全な保全、通知先側との照合、照合結果の承認と記録が必要である。今回の診断はその必要性を示すだけで、実行・復旧操作を実装していない。未解決状態の解除、実通知の到達確認、通知先/担当者、外部実行元、永続保存基盤、履歴保存期間は引き続き未実装または運営者判断待ち。公開メールやLINEを通知先に流用しない。
