# 外部異常通知の準備（未接続）

2026-10-16 UTC。今回追加したものは通知候補を作るオフライン処理であり、外部通知、外部定期実行、本番監視の稼働、通知到達は未完成。通知先は未設定、`enabled=false`、`destination=null`、自動再試行なしをコードで固定している。メール・LINE・HTTP送信、DB接続、ファイル保存、Cron登録、設定変更は行わない。

## 実装と対象

`scripts/prepare-cargo-monitor-notification.cjs` は既存の本番停止期間用分類器 `check-cargo-production-monitor.cjs` を再利用する。監視条件を二重実装せず、通知用の状態管理だけを追加した。現在の対象は `production-cargo-prelaunch-hold` の形式に限定し、検証DB内の監視行へ接続する処理は追加していない。形式ラベルは接続先を証明しない。

入力は既存の読取専用SQLのJSONと、前回の通知準備状態。出力は固定の環境ラベル、確認時刻、増加するイベント番号、固定の異常コード、解消した固定コード、送達確認状態だけに限定する。件数、申込者、メールアドレス、住所、任意のエラー本文、秘密値は転記しない。不正な入力/状態も固定コードのみで拒否する。

```sh
node scripts/prepare-cargo-monitor-notification.cjs < sanitized-input.json
```

入力の形は `{"snapshot": <既存SQLのJSON>, "state": <前回出力のstate>}`。初回のみstate省略可。読取自体が失敗した場合は `{"read_succeeded":false,"state": <前回state>}` とし、SQLエラー本文や接続情報を含めない。CLIの入力上限は65,536文字。`enabled`、通知先、任意時刻などを入力で追加することはできない。候補があっても `status=disabled` / `dispatches=0` を返し、送信しない。

## 異常・復旧・読取失敗

| 観測 | 通知候補 |
| --- | --- |
| 初回正常 | 候補なし。正常な基準だけ保持 |
| 異常の発生、異常コード集合の変化 | `anomaly`。現在の固定コードと解消したコード |
| 新しい正常読取で異常が解消 | `recovery`。現在は正常であることと解消したコード |
| SQL/接続失敗、不正/古い読取、過去の読取の逆転 | `monitor_read_failed` / `MONITOR_READ_FAILED`。業務上の異常が解消したとは扱わない |
| 読取失敗後、より新しい有効な読取を取得 | `monitor_read_recovered`。監視読取の復旧と現在の正常/異常を別々に示す。業務異常が残っている場合もそのコードを保持 |

読取失敗の前の結果を再利用して復旧扱いにしない。直前の有効な読取時刻より新しい結果が必要。古い正常結果による上書きを防ぎ、同一時刻なのに異常コードが変わる入力も読取失敗とする。監視の時刻が前の確認より逆行する場合は処理を拒否する。

## 重複抑止と失敗時の扱い

同じ状態の繰り返しではイベント番号・候補の作成時刻を変えない。候補を作っただけで送達済みにはしない。通知候補の最新1件だけを保持するため、無制限な履歴や待ち行列を作らない。状態変化で最新候補が置き換わる際は、直前候補の送達が確認済みかを区別する。個別の過去通知履歴の保存は未実装であり、保存期間も未設定。

将来の通知実行側に備え、通信しない純粋な状態遷移 `claimAttempt` / `settleAttempt` を用意した。実通知を実装する際は、送信前に `attempt_started` を排他的・永続的に記録し、その後に送達結果を `confirmed` / `failed` / `unknown` のいずれかへ確定する。候補形成だけでは送達確認しない。確認済み・失敗・結果不明・実行途中の同一候補は自動再試行できない。遅れて届いた旧イベントの結果で新イベントを送達済みに変更することも拒否する。

現時点では永続保存、排他的な実行、送信処理、到達確認がないため、これらの純粋関数の試験成功を実通知の重複防止保証と扱わない。試験内の送達結果は架空の入力のみ。実行側の再起動時に状態を初期化したり、既存イベントを手動で再送可能へ戻したりしない。実行途中・結果不明は運営者が送信先側と照合するまで保留する。

## 次に必要なこと

1. 運営者が通知先、確認担当・対応時間、必要な再通知方針、履歴保存方針を決める。公開連絡先・LINEを通知先へ自動転用しない。
2. DB外側の定期実行元と必要最小限の読取権限、秘密値の保管先、通知準備状態の排他的な永続保存を設計する。外部実行元自身の停止も別途検出する。
3. 通知先が決まった後、送信先の権限/応答と結果不明の扱いをレビューする。実通知の対象・本文・回数を具体化し、実行前にまとめて運営者の確認を得る。今回のコードは通知を有効化できないため、将来の送信接続は別変更で行う。
4. 将来の独立した承認済み試験で、定期起動、異常→復旧、監視自身の停止、通知失敗/結果不明、再起動時の重複抑止と到達を確認する。既存の本人メールE2Eや終了済み試験枠を使わない。
