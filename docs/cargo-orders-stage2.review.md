## B. 管理者の操作手順（開発候補）

1. 軽貨物管理者でログインし「相談・受注一覧」を開く。送信済み見積もりのある相談に受注パネルを表示する。
2. 元の相談と保存済み見積もりを読み、実際に顧客と確認した料金・集荷日時・必要なら配送日時・条件を入力する。日時は**日本時間**。合意確認日時・確認方法・確認メモも入力する。
3. 管理者が確認した合意記録であることをチェックし、内容確認後に「顧客との合意を記録」を押す。この段階では未受注のまま。
4. 記録した最新条件と本人の対応可否を確認し、別のチェック・確認操作で「管理者として正式受注を記録」を実行する。
5. 実際の進行に合わせ「配送準備中」「配送中」「配送完了」を順番に記録する。各操作には確認チェックと確認画面が必要。
6. 中止する場合は5文字以上の理由を記入し、明示確認する。完了・中止後は元へ戻せない。
7. 条件を変更した場合は新しい合意として記録し、適用中の条件と最新条件を比較して別操作で適用する。旧条件は履歴へ残る。
8. 合意・操作履歴で日本時間の記録日時、担当者ID、条件版・受注版を確認する。本人IDは「自分」と併記する。未取得の氏名を推測して表示しない。各50件ずつ続きを取得できる。

これは管理者が顧客と合意を確認した業務記録であり、顧客本人がアプリ上で認証・同意したという事実ではない。法的な契約成立時点をシステムが決定しない。

## C. 状態・誤操作・保存の保護

- 状態は `accepted → preparing → in_transit → completed`。途中の中止 `cancelled` も管理者が明示記録する。未適用の変更合意がある間は進行を止め、中止だけを許可する。
- 第1工程の期待版・DBロック・一意な操作IDをそのまま使う。画面内の処理中制御により、新機能と既存の審査/見積もり/終了操作が同時に走るのを防ぐ。
- 複数タブはWeb Locksで、同じ環境・管理者・相談の送信と照合解除を排他する。他タブの完了待ちを自動送信の待ち行列にはしない。未対応ブラウザでは受注管理は閲覧のみとし、変更・照合解除は行えない。
- 送信前に操作ID・相談ID・操作種別・期待版だけをブラウザへ保存する。合意条件、顧客の連絡先、メモ、認証情報は保存しない。保存できなければ送信を開始しない。
- 通信・15秒の待機期限・不正応答などで結果不明となった場合、再読込やブラウザ再開後も新しい操作を止める。履歴の同じ操作ID・種別を照合する。最新50件で見つからなければ過去ページも調べる。未発見を未処理と断定せず、停止を維持する。自動再送や強制解除は用意しない。
- 確定した競合は最新状態を取り直し、再確認を案内する。401/403では表示を消去する。書込自体が認証で確定拒否された場合だけ、その操作の準備記録を解除する。過去の結果不明操作は認証失敗では解除しない。
- 明示ログアウトや別利用者への切替でも表示を消去し、古い非同期応答で復活しない。条件・メモはHTMLとして実行せず文字として表示する。
- 受注状態を読めない、受注済み、結果不明の操作がある場合は旧「契約なし終了・保存保留解除」を隠す。受注保護そのものは第1工程のDBが担う。完了・中止も30日削除の対象にしない。
- 受注後の保存期間は未決定・自動削除保護のまま。未受注の「不成立終了後30日」は変更していない。
