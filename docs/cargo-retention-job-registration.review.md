# 定期削除ジョブの登録前ガード

2026-10-16 UTC。PR #5の匿名集計プレビューを置き換えず、登録前の既存ジョブ確認を補う。今回も本番・検証プロジェクトへの接続、ジョブ登録、停止状態の変更、実削除は行わない。初回SQL、cleanup関数、既存監視は無変更。

## 実装済みの範囲

`integrations/cargo-retention-job-guard/inventory.readonly.sql` はSELECTだけ。独立して接続先を確認した後、明示的な読取専用トランザクションで使う設計である。今回の実行先は専用の隔離PostgreSQLだけ。

- 固定の本番用2ジョブ名との一致、大小文字だけ異なる名前、別名で既存cleanup名を含むコマンドを拾う。稼働中・停止中を区別し、同名/別名の重複、別DBの設定も判定する。
- コマンドが既存cleanupの100件呼出しに正確に一致するか、名前と処理対象が整合するかを分類する。クエリ、任意ジョブ名、所有者、接続先DB名、接続先ホスト、実行間隔の原文を出力しない。
- 間隔は形式と同値グループだけを返す。これはCronの完全な構文検査でも承認済み設定との比較でもない。未決定の間隔を推測して正常扱いしない。
- 全体の可視件数、関連件数と関連詳細を照合する。詳細は出力保護のため最大1,000件とし、超過は未確認として止める。RLSで一部の行しか見えない状態、読取専用でない取得、5分超の古さ、詳細不足、不正な値を正常扱いしない。

`scripts/check-cargo-retention-job-registration.cjs` はJSONを受ける純粋な事前診断で、通信・登録・上書き・有効化・削除の経路を持たない。戻り値の `inventory_valid` は入力の整合性だけを示す。正常な空一覧でも `registration_allowed=false` / `execution_enabled=false`。CLIは必ず非0で終了し、終了コード0を登録許可に取り違えない。既存ジョブは停止中や設定一致の場合も必ず手動レビュー待ちにする。

無効案 `plan.disabled.json` は `enabled=false`、`registration_allowed=false`、`schedule=null`、アプリ履歴/Cron履歴の保存期間は両方nullのまま。planの書換えや余分な設定も独立した固定契約との照合で検知する。既採用の終了後30日・既存100件上限は変えない。

## 未実装・判断待ち

登録操作そのもの、原子的な登録/上書き防止、登録直前の排他、実行担当や実行頻度の承認、履歴の保存/削除は未実装。今回の読取から登録までの間に状態が変わる可能性があるため、将来この診断結果だけで登録してはならない。登録作業は別のレビュー済み変更として扱う。

コマンドの文字列照合はSQL解析ではなく、ラッパー経由や別サーバー・外部スケジューラーの実行経路を証明しない。`INDIRECT_JOB_AUDIT_REQUIRED` は常に残る。Cron未導入・権限不足・取得失敗は未確認であり、空一覧に置き換えない。接続先プロジェクトの正しさもJSONの形式ラベルからは証明しない。任意エラー本文をチャット/Git/診断へ出さず、固定コードで未確認と扱う。

運営者が決めるのは、実行頻度とアプリ履歴/Cron履歴の保存期間・確認担当。値が決まっても今回の無効案を変更するだけでは登録できない。今回の本番配備・登録・削除禁止は継続する。

## 新規検証の範囲

Nodeは空一覧でも登録不可、無効案の改変、停止中/稼働中、別名/大小文字/別DB、重複、設定不一致、不完全一覧、不正値、固定出力、入力上限を確認する。隔離PostgreSQLは今回追加したinventoryだけを実行し、Cron自体やcleanup関数は導入しない。RLSで隠れたジョブ、権限不足、Cron表なしも未確認として止まることを確認する。既存プレビュー15検査や完了済み本人試験は再実行しない。
